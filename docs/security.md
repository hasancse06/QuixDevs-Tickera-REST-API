# Security model and audit

The addon delegates authentication to WordPress. External clients use per-user Application Passwords over HTTPS. Cookie clients require a valid REST nonce; nonce checks are not replaced with a shared secret. The runtime never stores or logs authentication headers or passwords.

Object authorization combines strict actual authorship and WordPress mapped capabilities. Ticket access also requires its owned editable parent. Permissions are checked at the route, after lock acquisition and immediately before saving. Creator-only permissions can create a resource without conferring future editing access. Administrators do not bypass ownership. Foreign IDs use generic 404 responses.

Input/output use explicit allowlists. JSON object writes reject unknown keys, ownership reassignment and arbitrary metadata. Supported rich content uses wp_kses_post; titles/location use text sanitization. Clients must still render returned content safely. Date ranges, precise decimal strings, integer capacity bounds, category assignment and owned media/templates are validated. WordPress APIs perform post/meta/taxonomy writes; the only custom SQL uses prepared statements for connection locks. Metadata reads do not enumerate private keys, sold counts, order data or attendees.

Lists require author filtering, editable statuses, bounded page sizes (1–100) and fixed order/search fields; unsupported query parameters cannot override those constraints. Responses use private/no-store and vary by Authorization/Cookie. Totals describe the authorized database query at that instant; custom per-object capability filters and external concurrent writes may change later pages or cause defensive item omission. Do not share private response caches across identities. Rate limiting and request-body limits belong at the host; the addon adds no unbounded bulk API.

Related writes through this addon use nonblocking connection advisory locks keyed by site prefix and event (or creator for a new event). Failure/contention returns quixdevs_resource_busy/409. The service flushes stale post caches, recomputes combined dates and rechecks ownership under the lock. Finally blocks release locks after success and failure. These locks do not serialize native admin screens or other plugins. There is no ETag, optimistic version field, idempotency key or global transaction. WordPress hooks/meta writes may partially persist before a late failure; inspect before retrying creation. Operators must not assume exactly-once writes.

Tickera's real save_post lifecycle is retained while ambient admin-form $_POST is temporarily isolated to prevent admin hooks from accepting REST-unvalidated fields. The original form state is restored in finally. Runtime errors return safe generic messages, never database/exception details. Missing/unsupported Tickera returns 503; detected Bridge/custom relationship mode returns 409 for ticket operations.

Strict ownership applies only to this addon's namespace. Native Tickera, wp/v2 endpoints, dashboard access and other plugins retain independent policies. This audit does not certify the entire WordPress installation, premium Bridge or arbitrary third-party hooks. Report suspected issues privately to the publisher through https://quixdevs.com/; do not include credentials or private attendee data in a public issue.
